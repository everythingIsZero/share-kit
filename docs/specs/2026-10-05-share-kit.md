# 2026-10-05 分享能力统一：share.hxym18.com 中转 + 前端 SDK（share-kit）

> 本仓立项 spec（2026-10-05 定稿；同日自 sso-bridge 仓 docs/staging 迁入本仓）。
> 调研完成于 2026-10-05，资产盘点见文末 Working notes。

## 背景与使命

服务号「JS 接口安全域名」仅 5 席，且**父域不覆盖子域**（2026-10-05 实测口径：已配 hxym18.com 父域，子域仍不可用，须逐域添加；官方文档「绑定父级域名，其合法的子域名可用」与实测不符，以实测为准。现 4 席已用：hxym18.com / hmd / auth / fang）；网页授权域名 2 席已满（auth / hmd，子域同样不通用）。业务站数量（zbh / nuantie / card / wordinput…）已超 JS 名额余量，且各站分享实现各自为政（zbh 1063 行实战踩坑、nuantie 82 行弱化重写、老仓 packages 已有成熟决策层但无人用）。本轮把两件事一次收口：

1. **share.hxym18.com**：占用一个安全域名名额，全站分享链接统一收敛到 `share.hxym18.com/s/<shareId>`，中转页上做 JS-SDK 自定义卡片后跳转业务页 —— 突破名额限制。
2. **share-kit 前端 SDK**：终端兼容（PC 浏览器 / 微信内置 / 手机浏览器 / 小游戏）的海报分享操作（下载、保存、分享、复制）一次抽象，全站复用。

## 决策

### D1 路线：前端 SDK 为主 + share.hxym18.com 轻中转

- 分享的具体操作（环境判定、终端分流、海报渲染、下载保存）**全部在前端 SDK 完成**。
- 服务端不做重活：明确否决 Puppeteer 服务端渲染路线（zbh 已证明本地渲染可行且体验不差；服务端渲染重、慢、成本高）。
- share.hxym18.com 只承担：短链中转（302）、中转页静态 HTML（JS-SDK 卡片设置 + 跳转）、后续可选的图片代理/小程序码。
- JS-SDK 签名**复用 sso-bridge** `POST /api/wechat/jsapi-sign`（白名单 `*.hxym18.com` 全域已覆盖，零改动）。

### D2 SDK 分层（不绑定技术栈，小游戏可用）

```
share-kit（独立仓 everythingIsZero/share-kit，git 依赖引用）
├── core/          决策层：环境指纹 → 唯一动作 + 事前说明 + 结果分类
├── web/           浏览器适配层：collectSignals / executeAction / report + React 可选绑定
├── poster/        海报配置：业务数据 → 冻结快照（纯函数、纯数据，无 DOM/canvas 依赖）
├── render-dom/    DOM→canvas 渲染器（html2canvas-pro + qrcode；浏览器专用）
└── render-canvas/ 纯 canvas 手绘渲染器（共用 poster 配置；小程序/小游戏用）
```

- `core/`、`poster/` 零依赖纯函数：小游戏（LayaAir）环境直接可用。
- `render-dom/` 唯一重依赖 html2canvas-pro + qrcode；React 是可选 peer（不 import `/react` 不拉起 React）。
- 六动作已含小程序/小游戏语义（`save.album` / `share.card.miniapp`）；**Taro / LayaAir 适配层本轮不建**（YAGNI），端接入时按 core 契约补。

### D3 平移来源（不重写）

| 包 | 来源 | 动作 |
|---|---|---|
| core/ | 老仓 `packages/share-core`（probe / capability-table / decide / actions / copy / outcome） | 整体平移，测试全量带走 |
| web/ | 老仓 `packages/share-web`（collect-signals / execute / report / react） | 整体平移，测试全量带走 |
| poster/ | nuantie `lib/poster/config.ts`（冻结快照思路） | 提炼为通用 schema（业务字段泛化） |
| render-dom/ | zbh `PosterRenderer.tsx` 渲染管线（1000+ 行中的渲染部分） | 抽出渲染器 + 全部坑位纪律 |

规范随包迁移：老仓 `docs/multi-platform-spec.md` 第六节 12 条红线并入 share-kit README。

### D4 服务端契约（share.hxym18.com）

```
GET  /s/:shareId        → 302 业务页；UA 为分享爬虫时返回中转页 HTML（og meta）
GET  /s/:shareId/page   → 中转页 HTML：JS-SDK 自定义卡片 → 跳转业务页
POST /api/shares        → 业务方注册分享（secret 鉴权，同 sso-bridge x-auth-secret 口径）
```

- share 记录字段：`shareId`（短 ID）、`target_url`、`card{title,desc,thumb_url}`、`owner`（业务方标识）、`created_at`。
- 存储/部署形态：**deferred**（起服务时另项调研；倾向复用现有 docker compose 基础设施）。
- **M2 前置**：JS接口安全域名须显式添加 `share.hxym18.com`（父域不覆盖子域，见背景实测口径；添加时需域名根目录可访问 MP_verify 校验文件，服务上线后自然满足；第 5 席加满，或确认根域 hxym18.com 无页面在用 JS-SDK 后替换之以留余量）。网页授权域名不动（2/2 满，share 中转页无 OAuth 需求）。

### D5 业务站接入（四步，一次做完全站受益）

1. `bun add github:everythingIsZero/share-kit`（git 依赖，无 registry 维护成本）。
2. 生成海报：业务数据 → `poster/` 冻结快照 → `render-dom/` → image blob（独立方法链）。
3. 分享操作：blob 填进 artifact 交给 `ui/mountShare` —— 按钮点击**先弹海报预览层**（图是基本操作：大图 + 层内方式按钮，主推荐高亮，微信内长按大图即保存 / 转发），手机浏览器系统面板、桌面下载全在 SDK 内，无需写环境分支、无需处理点击重决策。
4. 分享链接统一 `share.hxym18.com/s/<shareId>`（复制链接 / 卡片 / 海报二维码同源）。

## 不变量

- core 零宿主依赖（node:test 全覆盖）；加环境只加能力表行，不加 if。
- 点击先见图再选方式（2026-10-05 出资人拍板）：图片产物先弹海报预览层（大图 + 层内方式按钮行 + 长按提示），方式只列该环境真实可用的项（能力表 + 运行时信号双重过滤，绝不列会失败的项），偏好序第一项高亮为主推荐；`preview.longpress` 不渲染按钮——大图本身可长按；`copy.link` 恒可作为次要项。无图可显（link / video 产物、图未就绪）弹 Action Sheet 兜底，其中唯一可用动作时不弹直接执行。执行在手势同步段发起（R14，先 await 会烧掉用户激活）。
- 未实测能力格不给强引导（R16）；`available: null` 不冒充已知。
- UA 原文与身份字段不进上报事件；取消与失败分开归因。
- 海报渲染前冻结数据快照（防幽灵数据）。
- render-dom 微信铁律：不用 SVG 图标、不用 relative/absolute 定位、外链图走同源代理、二维码 512px 源图 + 导出后重绘、scale 预算防 iOS 画布超限、toBlob 失败降级 dataURL。

## Working notes

### 资产盘点（2026-10-05 调研结论）

- **老仓 `packages/share-core` + `share-web`**：设计成熟（决策/执行分离、42 格能力表、R1-R17 红线），唯一接入方 fang（workspace 协议，2026-09-18 已部署）。已踩坑：接入方 Dockerfile 必须 COPY 两包源码 + pnpm --filter 带省略号（git 依赖独立仓后此坑自然消失）。
- **zbh `PosterRenderer.tsx`**（1063 行）：渲染实战库。关键坑：snapdom（SVG foreignObject）在微信 iOS WKWebView 被证伪 → html2canvas-pro；Tailwind v4 oklch 需 pro 版；微信内 a[download] 拦截 → 长按预览层；navigator.share + canShare 文件分享；clipboard 静默失败兜底。
- **nuantie `lib/poster/`**：抽象 v1 未完善（render-h5 82 行简版未落全坑；weapp 渲染器未实现；与老仓 core 未打通，属重复发明）。
- **sso-bridge**：`/api/wechat/jsapi-sign` 已上线，白名单 `*.hxym18.com`。

### 被否决的方向

- **方案 B 服务端渲染**：重、慢、成本高，zbh 已证明本地渲染可行。
- **新工作区 monorepo 化**：要动现有独立仓结构，改动面过大。
- **GitHub Packages**：独立开发者维护 registry + token 成本偏高，git 依赖够用。
- **core 吸收 nuantie share.ts（Taro 入口）**：绑定 Taro 违反「不绑定技术栈」，由未来端适配层承接。

### 开放问题

- 中转服务部署形态与存储选型（deferred，起服务时调研）。
- 海报二维码指向：直接业务页 or share 短链？（倾向短链：扫码后的分享链路与入口统一，但多一跳——首个业务站接入时实测再定。）
- 二次分享卡片回落：中转页 A → 业务页 B 后，用户在 B 内再分享的卡片是 B 的默认卡片（域名名额限制无法覆盖 B）。可接受，不做特殊处理。
